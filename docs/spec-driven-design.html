What Is It?
Engineering the inputs
An LLM is only as good as the context it receives. Spec-driven design means writing that context deliberately — before a single line of code runs.
Step 01
Write the spec
Document what you want to build, why, and what success looks like. Use structured markdown files.
→
Step 02
Give AI full context
Load the spec at the start of every session. Claude always knows the mission, constraints, and current state.
→
Step 03
Execute & verify
Claude builds task by task. You verify against the spec. Accurate and resumable across every session.
"Stop writing code, start writing contracts."
— Spec-Driven Development · Max & Maria, SC Engineering

Method 01
OpenSpec
A structured change workflow. Claude must write a full proposal — what it'll build and why — before touching any files.
✓
UI & prototype work — explicit design intent, not guessed
✓
Multi-step changes — tracked in tasks.md, resumable any time
✓
Exploring without committing — think with Claude, touch nothing
✕
Quick one-liner fixes — just prompt directly
★ Used on — the Quick Secure Auth native prototype
The Flow
/openspec-propose
Claude writes the full proposal before any code runs.
→ proposal.md · design.md · tasks.md
/openspec-apply-change
Implements task by task. Each task is verified before moving on.
/openspec-critique-change
Deliberate review against the proposal. Flags drift early.
Four Modes
/feature
Title without touching code
/compose
Generates full change package
/reply
Execute task by task
/iterate
Finalise & close

Method 04
ODD
Outcome-Driven Development — design-first. You start with what a real person should be able to do when the work is done, not a feature spec.
✓
You're designer and builder — design language drives the build
✓
Verified delivery matters more than speed
✕
Speed is the constraint — use OpenSpec instead
✕
Just shipping a single change, not building a product
Core Concepts
Personas
The real people the work is for — with goals, context, and environment
Outcomes
What each persona can do when the work succeeds — not features, abilities
Contracts
Interfaces between outcomes so they can be built independently and in parallel
Verification
Walk through the outcome in a browser before it's marked done. Domain language only
Personas → Outcomes → Build → Verify in browser → Commit → Next outcome
